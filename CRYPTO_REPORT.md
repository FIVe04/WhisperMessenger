# Криптографический отчёт по проекту Whispre

## 1. Область отчёта

Документ описывает криптографию, фактически реализованную в текущем
iOS-клиенте и backend. Основной клиентский код находится в:

- `WhispreClient/WhispreClient/App/Core/CryptoService.swift`;
- `WhispreClient/WhispreClient/App/Core/KeychainStore.swift`;
- `WhispreClient/WhispreClient/App/Core/SessionStore.swift`;
- `WhispreClient/WhispreClient/App/State/AppState.swift`.

Сервер принимает только открытый ключевой материал, ciphertext и метаданные.
Приватные ключи и plaintext серверу не передаются.

## 2. Используемые примитивы

### 2.1. X25519

`Curve25519.KeyAgreement` из CryptoKit используется для:

- identity key pair устройства;
- signed prekey;
- one-time prekeys;
- ephemeral key исходящей сессии;
- вычисления общих секретов между отправителем и получателем.

Открытые и приватные ключи X25519 имеют размер 32 байта. В REST и JSON они
передаются в Base64.

### 2.2. Ed25519

`Curve25519.Signing` используется как identity signing key. Устройство
подписывает 32-байтное представление своего signed prekey. Подпись имеет размер
64 байта.

При получении key bundle клиент:

1. декодирует identity key, signing key и signed prekey из Base64;
2. проверяет, что ключи имеют допустимое представление Curve25519;
3. проверяет Ed25519-подпись signed prekey;
4. проверяет формат one-time prekey, если он выдан.

Сервер проверяет размер и Base64-формат полей, но криптографическую подпись
проверяет именно iOS-клиент.

### 2.3. HKDF-SHA256

HKDF-SHA256 используется в два этапа. Сначала каждый результат X25519
преобразуется в отдельный 32-байтный компонент с контекстной меткой. Затем
компоненты объединяются и передаются во второй HKDF вместе с контекстом:

- ID диалога;
- ID устройства отправителя;
- ID устройства получателя;
- ID сессии;
- ID signed prekey;
- ID one-time prekey или значение `none`.

Результатом является симметрический ключ длиной 32 байта.

### 2.4. ChaCha20-Poly1305

`ChaChaPoly` из CryptoKit используется для AEAD-шифрования текста сообщения.
CryptoKit формирует случайный nonce и возвращает combined-представление,
содержащее nonce, ciphertext и authentication tag.

ChaCha20-Poly1305 обеспечивает конфиденциальность и проверку целостности
сообщения при условии сохранения секретности ключа и отсутствия повторного
использования nonce с тем же ключом.

### 2.5. Bcrypt, SHA-256 и JWT

Серверная аутентификация использует отдельные механизмы:

- пароль сначала хэшируется SHA-256, результат кодируется Base64 и передаётся
  в bcrypt;
- access и refresh JWT подписываются HS256;
- refresh token хранится в PostgreSQL в виде SHA-256-хэша;
- access token действует 900 секунд;
- refresh token действует 2 592 000 секунд и ротируется при обновлении.

JWT обеспечивает целостность и аутентичность токена, но не шифрует его
содержимое.

### 2.6. Base64

Base64 используется только как транспортное кодирование бинарных ключей,
подписей и ciphertext. Base64 не является шифрованием и не добавляет
криптографической защиты.

## 3. Регистрация устройства и key bundle

При входе пользователя `AppState.registerCurrentDevice()` запрашивает у
`CryptoService` регистрационный bundle. Если соответствующих приватных ключей
ещё нет в Keychain, клиент создаёт:

- identity X25519 key pair;
- identity Ed25519 signing key pair;
- signed X25519 prekey с идентификатором `1`;
- десять one-time X25519 prekeys с идентификаторами `100001`-`100010`.

Signed prekey подписывается приватным Ed25519-ключом. На сервер отправляются:

- открытый identity key;
- открытый identity signing key;
- ID и открытая часть signed prekey;
- подпись signed prekey;
- открытые части one-time prekeys.

`auth-service` сохраняет устройство и key bundle. Повторная регистрация того же
device ID обновляет bundle. One-time prekeys вставляются с ограничением
уникальности `(device_id, prekey_id)`.

## 4. Получение one-time prekey

Перед созданием исходящей сессии клиент вызывает:

`POST /v1/keys/users/{user_id}/one-time-prekey/claim`.

`key-service` выбирает активное устройство пользователя и выполняет выборку
свободного ключа с `SELECT ... FOR UPDATE SKIP LOCKED`. Выбранный ключ
помечается как использованный в той же транзакции.

Если one-time prekeys закончились, сервер возвращает `409 Conflict`. Текущий
iOS-клиент в этом случае получает обычный bundle без one-time prekey и создаёт
сессию на основе трёх обязательных X25519-компонентов.

## 5. Установление исходящей E2E-сессии

Для новой пары устройств и диалога отправитель:

1. получает и проверяет key bundle получателя;
2. создаёт или восстанавливает ephemeral X25519 key;
3. вычисляет три обязательных общих секрета:
   - `IK_sender x SPK_recipient`;
   - `EK_sender x IK_recipient`;
   - `EK_sender x SPK_recipient`;
4. при наличии one-time prekey вычисляет:
   - `EK_sender x OPK_recipient`;
5. выводит общий симметрический ключ через HKDF-SHA256.

Схема по структуре похожа на этап первоначального обмена X3DH, однако является
собственной реализацией проекта и не должна называться полной реализацией X3DH
или Signal Protocol.

Исходящая сессия привязана к:

- пользователю и устройству отправителя;
- пользователю и устройству получателя;
- диалогу.

Состояние сессии, включая ephemeral private key и открытые ключи получателя,
сохраняется в Keychain.

## 6. Формирование зашифрованного конверта

После шифрования клиент формирует JSON payload со следующими полями:

- `v` - версия криптографического формата;
- `alg` - строка `X25519+ChaCha20-Poly1305`;
- `sid` - идентификатор сессии;
- `senderIdentityPub` - открытый identity key отправителя;
- `senderEphemeralPub` - открытый ephemeral key;
- `recipientIdentityPub` - открытый identity key получателя;
- `signedPrekeyID` и `oneTimePrekeyID`;
- `ct` - Base64 от combined-представления ChaCha20-Poly1305.

JSON кодируется в Base64 и получает префикс `e2e1:`. В отдельном
`header` конверта передаются служебные поля протокола, включая ephemeral public
key и идентификаторы использованных prekeys.

Новые сообщения создаются с `protocol_version = 2`. Название поля
`ratchet_pub` сохранено в API-контракте, но Double Ratchet не реализован: поле
содержит идентификатор сессии и открытый identity key отправителя.

## 7. Отправка и серверное хранение

Зашифрованный конверт отправляется через:

`POST /v1/messages/envelopes:batch`.

`message-service` проверяет права участников и устройств, формат UUID,
префикс `e2e1:`, обязательные поля заголовка и идемпотентность batch. После
этого в PostgreSQL сохраняются:

- ciphertext;
- открытый header;
- идентификаторы пользователей, устройств и диалога;
- время отправки, приёма, доставки и подтверждения.

Сервер не хранит отдельного поля plaintext и не имеет приватных ключей,
необходимых для штатного расшифрования сообщения.

При этом сервер видит метаданные: участников, устройства, диалог, время,
размер и частоту сообщений, факт доставки и подтверждения, а также открытые
поля E2E-заголовка.

## 8. Получение и расшифрование

WebSocket передаёт клиенту только событие `new_envelope`. После него клиент
запрашивает pending-конверты через REST.

Получатель извлекает из payload и header:

- открытый identity key отправителя;
- открытый ephemeral key отправителя;
- ID signed prekey и one-time prekey;
- идентификатор сессии.

Затем он выполняет симметричные стороне отправителя операции X25519,
HKDF-SHA256 и `ChaChaPoly.open`.

Если ciphertext повреждён, ключевой материал отсутствует или authentication
tag не проходит проверку, интерфейс показывает безопасную заглушку:

`Encrypted message (unavailable on this device)`.

Для старых сообщений версии 1 в коде существует совместимый путь со статическим
X25519 identity key agreement. Новая отправка использует prekey-формат версии 2.

## 9. Хранение секретов на клиенте

`KeychainStore` создаёт записи с атрибутом
`kSecAttrAccessibleAfterFirstUnlockThisDeviceOnly`. В Keychain находятся:

- access и refresh tokens;
- приватный X25519 identity key;
- приватный Ed25519 signing key;
- приватный signed prekey;
- приватные one-time prekeys;
- исходящие криптографические сессии.

Device ID, user ID, username и несекретные флаги состояния хранятся в
`UserDefaults`. При обнаружении данных старого формата клиент переносит токены,
identity key и сессии из `UserDefaults` в Keychain.

Обычный logout удаляет токены, но сохраняет криптографические ключи и device ID,
что позволяет тому же аккаунту повторно использовать зарегистрированное
устройство. При этом текущий iOS-клиент не вызывает серверный
`POST /v1/auth/logout`, поэтому сохранённая на сервере refresh-сессия не
отзывается самим клиентским logout. `Reset App Data` удаляет Keychain-материал
и создаёт новый локальный device ID.

## 10. Свойства и ограничения

Фактически обеспечиваются:

- шифрование и расшифрование текста на конечных устройствах;
- AEAD-проверка целостности ciphertext;
- проверка подписи signed prekey на клиенте;
- одноразовая серверная выдача one-time prekey;
- отсутствие plaintext и приватных ключей в backend-контракте;
- защита секретного локального материала средствами iOS Keychain.

Не обеспечиваются или не подтверждены:

- Double Ratchet;
- отдельный ключ для каждого сообщения;
- post-compromise security;
- полная forward secrecy истории;
- защита от злонамеренной подмены всего identity bundle сервером;
- пользовательская сверка fingerprint;
- multi-device синхронизация;
- резервное копирование или перенос ключей на новое устройство;
- формальная верификация и независимый криптографический аудит.

Схема также не скрывает метаданные и не защищает plaintext на
скомпрометированном конечном устройстве.

## 11. Транспортная безопасность

Локальная конфигурация использует `http://localhost:8000` и прямой WebSocket к
`http://localhost:8006`. TLS и certificate pinning в проекте не настроены.

Для публичного развёртывания необходим HTTPS/WSS reverse proxy и безопасное
управление секретами. Без TLS локальная E2E-схема защищает содержимое
конвертов, но токены, пароли при входе и сетевые метаданные не защищены от
перехвата транспортного трафика.

## 12. Корректная формулировка для ВКР

Реализацию можно описывать как:

> Клиентская схема сквозного шифрования на основе X25519, подписанного prekey,
> одноразового prekey, HKDF-SHA256 и ChaCha20-Poly1305.

Допустимо указывать, что установление сессии спроектировано по мотивам prekey-
подхода Signal/X3DH. Нельзя утверждать, что проект реализует Signal Protocol,
Double Ratchet, доказанную криптографическую безопасность или полную
защищённость production-мессенджера.
