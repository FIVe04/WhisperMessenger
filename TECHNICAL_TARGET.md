# Whispre: технический профиль реализованного MVP

## 1. Назначение

Whispre - прототип iOS-мессенджера со сквозным шифрованием и backend на
микросервисной архитектуре. Проект предназначен для демонстрации следующего
сценария:

- регистрация и аутентификация пользователя;
- регистрация одного устройства пользователя;
- публикация набора открытых ключей устройства;
- поиск пользователя и создание личного диалога;
- установление E2E-сессии между двумя устройствами;
- клиентское шифрование сообщения и передача зашифрованного конверта;
- хранение ciphertext и служебных метаданных на сервере;
- доставка сообщения через REST и уведомление через WebSocket;
- локальная расшифровка истории на iOS-клиенте;
- подтверждение обработки сообщения получателем.

Проект следует позиционировать как production-oriented MVP, а не как полный
аналог Signal. В нём реализована собственная prekey-схема, близкая по общей
идее к X3DH, но отсутствует Double Ratchet и формальная совместимость с Signal
Protocol.

## 2. Реализованная архитектура

Backend состоит из восьми FastAPI-сервисов:

- `api-gateway` - HTTP-прокси, проверка access token и лимит запросов;
- `auth-service` - регистрация, вход, обновление и отзыв refresh token,
  регистрация устройства;
- `user-service` - профиль текущего пользователя и поиск пользователей;
- `key-service` - получение key bundle, атомарная выдача one-time prekey и
  пополнение ключей;
- `conversation-service` - создание и получение личных диалогов;
- `message-service` - проверка маршрута конверта, сохранение ciphertext,
  выдача истории и подтверждение доставки;
- `realtime-service` - авторизованные WebSocket-подключения устройств и
  доставка событий о новых конвертах;
- `notification-service` - временная очередь уведомлений в памяти процесса.

PostgreSQL является общей базой данных сервисов. Доступ к ней реализован через
SQLAlchemy 2.x и синхронный драйвер psycopg 3. История схемы управляется
Alembic.

Kafka используется в фактическом сценарии для события
`message.envelope.accepted.v1`: `message-service` публикует его после сохранения
конверта, а `realtime-service` и `notification-service` обрабатывают независимо
в разных consumer groups.

Redis присутствует в локальном Compose-стенде и передаётся некоторым сервисам
через переменные окружения, но текущая бизнес-логика его не использует.
Rate limiter, WebSocket-соединения и очередь notification-service хранят
состояние в памяти соответствующего процесса.

## 3. Криптографическая модель

Ключевой материал создаётся только на iOS-клиенте с использованием CryptoKit:

- X25519 identity key pair;
- Ed25519 identity signing key pair;
- X25519 signed prekey;
- набор из десяти X25519 one-time prekeys;
- X25519 ephemeral key отправителя для исходящей сессии.

Открытая часть key bundle загружается на сервер. Signed prekey подписывается
Ed25519-ключом устройства. Перед созданием исходящей сессии клиент проверяет
формат всех открытых ключей и подпись signed prekey.

Сессионный ключ формируется из трёх обязательных и одного опционального
результата X25519:

1. identity key отправителя и signed prekey получателя;
2. ephemeral key отправителя и identity key получателя;
3. ephemeral key отправителя и signed prekey получателя;
4. ephemeral key отправителя и one-time prekey получателя, если он доступен.

Компоненты обрабатываются HKDF-SHA256 и объединяются повторным HKDF-SHA256 в
256-битный симметрический ключ. Сообщение шифруется ChaCha20-Poly1305.

Ciphertext имеет строковый префикс `e2e1:`. После префикса находится Base64 от
JSON-контейнера с версией протокола, идентификатором сессии, открытыми ключами,
идентификаторами prekey и результатом AEAD-шифрования. Сервер проверяет только
формат конверта и не выполняет расшифрование.

## 4. Ограничения криптографической модели

В проекте отсутствуют:

- Double Ratchet и обновление ключа для каждого сообщения;
- post-compromise security;
- полноценная forward secrecy для всей истории переписки;
- верификация пользователями fingerprint или safety number;
- криптографическое связывание учётной записи с identity key вне доверия к
  серверу выдачи ключей;
- независимый аудит криптографического протокола.

Повторные сообщения в рамках исходящей сессии используют один производный
симметрический ключ, при этом ChaCha20-Poly1305 получает новый случайный nonce
от CryptoKit. В коде сохранён путь расшифрования старого формата версии 1 на
основе статического X25519, но новые сообщения создаются в формате версии 2.

Поэтому корректная формулировка для ВКР: в проекте реализовано прикладное
сквозное шифрование с prekey-установлением сессии. Называть реализацию полным
Signal Protocol нельзя.

## 5. Серверные проверки безопасности

`message-service` перед сохранением конверта проверяет:

- соответствие `sender_user_id` пользователю из access token;
- единое устройство отправителя для всего batch;
- участие отправителя и получателя в указанном диалоге;
- принадлежность активного устройства отправителю;
- принадлежность активного устройства получателю;
- UUID идентификаторов;
- наличие префикса `e2e1:`;
- обязательные поля заголовка и версию протокола;
- уникальность пары `sender_device_id` и `idempotency_key`.

`key-service` и `auth-service` проверяют размер Base64-представлений открытых
ключей и подписи. One-time prekey выдаётся транзакционно с
`SELECT ... FOR UPDATE SKIP LOCKED`, после чего помечается использованным.
Владельцем изменяемого key bundle или набора prekeys должен быть текущий
пользователь.

Access и refresh tokens подписываются HS256. Access token действует 15 минут,
refresh token - 30 дней. Refresh token хранится на сервере в виде SHA-256-хэша
и ротируется при обновлении. Пароль предварительно хэшируется SHA-256 для
устранения ограничения bcrypt в 72 байта, затем обрабатывается bcrypt.

## 6. Хранение данных на iOS

В Keychain хранятся:

- access и refresh tokens;
- приватные identity, signing, signed prekey и one-time prekey;
- состояние исходящих криптографических сессий, включая ephemeral private key.

В `UserDefaults` хранятся только несекретные данные состояния интерфейса:
идентификаторы пользователя и устройства, имя пользователя, привязка аккаунта
к локальному device ID и признак завершённой регистрации. Код также переносит
старые токены и криптографические сессии из `UserDefaults` в Keychain, если
обнаруживает их.

Локальная база сообщений отсутствует. После запуска клиент получает историю
зашифрованных конвертов с сервера и расшифровывает её в памяти.

## 7. Доставка сообщений

Отправитель передаёт batch конвертов через API Gateway. После успешной
транзакции PostgreSQL `message-service` публикует Kafka-событие и возвращает
`202 Accepted`.

`realtime-service` отправляет получателю событие `new_envelope`. Сам ciphertext
через WebSocket не передаётся: событие служит сигналом клиенту выполнить
`GET /v1/messages/envelopes/pending`. Получение pending-конвертов устанавливает
`delivered_at`, после локальной обработки клиент вызывает ACK, который
устанавливает `acked_at`.

Если WebSocket недоступен, непрочитанный конверт остаётся в PostgreSQL и может
быть получен после повторного входа или восстановления соединения.

Между фиксацией конверта в PostgreSQL и публикацией Kafka-события нет
Transactional Outbox. При сбое Kafka после коммита конверт сохранится, но
realtime-событие может не быть опубликовано; pending polling остаётся
механизмом восстановления.

## 8. Жизненный цикл устройства

Текущая реализация работает в однопользовательском и одноустройственном режиме:

- сервер допускает только одно активное устройство на аккаунт;
- установка iOS-приложения закрепляется за первым вошедшим аккаунтом;
- обычный logout удаляет локальные токены, но сохраняет device ID и ключи;
- iOS-клиент при logout не вызывает серверный `/v1/auth/logout`, поэтому
  соответствующий refresh token остаётся действительным до ротации, истечения
  срока или отдельного вызова endpoint;
- повторный вход того же пользователя восстанавливает то же устройство;
- для смены аккаунта на одной установке требуется `Reset App Data`;
- endpoint деактивации или контролируемой замены устройства отсутствует.

Вход существующего аккаунта на новом устройстве будет отклонён, пока в БД есть
другое активное устройство. Полноценный multi-device и controlled device
replacement не реализованы.

## 9. Наблюдаемость

Каждый FastAPI-сервис предоставляет:

- `GET /health` для проверки процесса;
- `GET /metrics` с HTTP-, Kafka- и WebSocket-метриками;
- структурированные JSON-логи в stdout;
- `X-Request-ID` в HTTP-ответах.

Prometheus опрашивает сервисы, Grafana показывает общий дашборд, Alloy собирает
контейнерные логи через Docker-совместимый сокет, Loki хранит их семь дней.
Предусмотрены правила оповещения о недоступности сервисов, высокой доле 5xx и
высокой p95-задержке.

Endpoint `/ready` и проверки доступности зависимостей в health response сейчас
не реализованы.

## 10. Тестирование

В репозитории есть интеграционный smoke test из десяти шагов. Он проверяет:

- доступность API Gateway;
- регистрацию двух пользователей и устройств;
- публикацию и выдачу key bundle;
- получение one-time prekey;
- создание личного диалога;
- отказ при подмене устройства получателя;
- приём корректного encrypted envelope;
- pending и историю сообщений;
- ACK и исключение подтверждённого конверта из pending.

Smoke test использует синтетические Base64-данные и проверяет серверный
контракт, но не выполняет реальное шифрование CryptoKit. Отдельного набора unit,
нагрузочных, отказоустойчивых и криптографических тестов в проекте нет.

## 11. Границы демонстрационного стенда

Локальный стенд работает по HTTP и WebSocket без TLS. Секреты и пароли Compose
имеют демонстрационные значения. Для публичного развёртывания необходимы
HTTPS/WSS, секреты из защищённого хранилища, сетевое ограничение внутренних
сервисов, постоянное хранилище очередей и production-настройка Kafka и
PostgreSQL.

Не реализованы вложения, APNs push-уведомления, групповые чаты в iOS-интерфейсе,
удаление аккаунта и горизонтальное масштабирование stateful-компонентов.

## 12. Критерий готовности к защите

Проект готов к демонстрации как бакалаврский прототип, если:

- миграции Alembic и Compose-стенд запускаются с чистой базой;
- smoke test завершается сообщением `SMOKE TEST PASSED`;
- два iOS Simulator обмениваются сообщениями в реальном времени;
- в PostgreSQL демонстрируется `ciphertext` с префиксом `e2e1:`, а не plaintext;
- в Grafana отображаются метрики и JSON-логи;
- ограничения протокола и локального стенда прямо указаны в тексте ВКР.
